# AGENTS.md

Shared instructions for every coding agent working in this repository (Claude Code, Codex, Cursor, Antigravity and others). This file is the single source of truth for how to work here. `CLAUDE.md` imports it.

## The project

An engineering thesis application: a progressive web app (PWA) for logging and analysing combat-sports training, built on a cloud backend (BaaS). Thesis title (Polish): *Projekt i implementacja progresywnej aplikacji internetowej wspomagającej ewidencję i analizę treningów sportów walki w oparciu o architekturę chmurową.*

- The thesis card in `combat-training-app/docs/thesis-card.md` is the top-level requirement. The topic is binding; technologies and the feature list in the card are a starting point and may be replaced by better options when the decision is recorded.
- Disciplines: boxing, kickboxing, Muay Thai, K-1, MMA striking. One user is one athlete (no coach role yet).
- The primary device is a smartphone; the app must also work on desktop.
- Final application deadline: around 16 December 2026. Quality beats speed.

## Commands

Run from `combat-training-app/` with npm (never pnpm or yarn):

```bash
npm ci              # install exact dependencies
npm run dev         # local dev server
npm run typecheck   # TypeScript, no emit
npm run lint        # ESLint
npm test            # Vitest, single run
npm run build       # typecheck + production build
```

## Definition of done

A change is done only when all of these hold:

1. `npm run typecheck`, `npm run lint`, `npm test` and `npm run build` pass. CI runs the same checks on every pull request.
2. New or changed logic has tests. Pure calculations and timer behaviour use unit tests with a controlled clock.
3. No `any`, `@ts-ignore` or `eslint-disable` without a written justification in the code.
4. The pull request description says what changed, why, and how it was verified (commands run, screenshots for UI).

Report failures honestly. Never weaken a test, a type or a lint rule just to make a check pass.

## How to work

- **One task, one branch, one pull request.** Name branches `feat/…`, `fix/…`, `test/…`, `chore/…`, `docs/…`. Never commit to `main`, never force-push, and never work on a branch another agent is using.
- **Read before changing.** Read the relevant files and the matching document in `docs/` first (see the map below).
- **Small, reviewable commits** with Conventional Commit messages (`feat(player): …`). Do not touch unrelated files and do not reformat code you did not change.
- Keep visual changes, architecture changes and business-logic changes in separate pull requests. Propose a redesign before implementing it.
- **Decisions belong to the owner.** If a task needs a product or architecture decision that is not recorded in `docs/` or `docs/adr/`, stop and ask instead of guessing. Do not silently expand scope.
- **Record hard-to-reverse decisions** as a short ADR in `docs/adr/` (next free number, one paragraph is enough).
- If a change threatens the deadline, say so and propose the smallest usable alternative.

## Architecture

- Feature modules live in `src/features/<feature>`. Stable, framework-independent types and calculations live in `src/domain`. External integrations (Firebase, storage, audio, Wake Lock) live in `src/infrastructure` behind repository or service interfaces from `src/application`.
- React components never call Firebase directly and never contain domain calculations in JSX.
- Validate every external input (storage, network, database) at the infrastructure boundary with `zod/mini` schemas. Forms use controlled inputs and a tested validation function, without a form library. See `docs/adr/0006-validation-with-zod-mini.md`.
- Shared UI goes to `src/components` only when genuinely reused; otherwise it stays in its feature.
- Prefer named exports. No global state library without a demonstrated need. No speculative abstractions.

## Data and backend

- Backend: Firebase (Authentication, Cloud Firestore in `europe-central2`, Hosting) on the free Spark plan. See `docs/adr/0004-firebase-as-baas.md`, which supersedes ADR 0001.
- Authentication: email and password with email verification and password reset, plus Google sign-in. No anonymous mode. A user whose email address is not verified does not get into the app. See `docs/adr/0002-email-password-and-google-auth.md`.
- User data lives under `users/{uid}/…`. Firestore Security Rules allow access only to the owner and validate fields. Every rule change has tests with `@firebase/rules-unit-testing` on the emulator, including attempts by a second account and by a signed-out user.
- Firestore uses `persistentLocalCache` with `persistentMultipleTabManager`. The UI never waits for a write to reach the server; it shows a "waiting to send" state from `hasPendingWrites`. Load Firestore after the first render, not in the initial bundle. On sign-out, clear the local Firestore cache.
- Firestore has no schema: validate every document read or written at the infrastructure boundary and keep a `schemaVersion` field in stored documents. Field names use English `camelCase`.
- Tests and local development use the Firebase Emulator Suite with a `demo-` project ID. Tests never touch the real project.
- Never put a service account key or the Admin SDK in the frontend, and never commit secrets. The Firebase web config is public by design but still comes from `.env` (see `.env.example`).
- Historical workout snapshots must not change when library records change: store an immutable exercise-name snapshot and keep `combinationId` when available.
- Keep seed and demo data separate from user data.

## Workout player

Read `docs/workout-player-spec.md` before changing the player.

- Remaining time is always computed from a deadline and the current clock, never by decrementing once per second. Pause stores the remaining duration; resume creates a new deadline.
- The player must stay correct after the tab is hidden or the phone screen turns off and back on.
- Exercise ratings are collected after the workout on the summary screen, not during rest in the player.

## UI

Read `docs/design-system.md` before UI work.

- Dark mode exists; a light mode with a remembered user choice is required for the final version. Use theme tokens, never hard-coded colours.
- Near-black charcoal, off-white and a restrained blood-red accent. Angular geometry, 0–4 px radii. No glassmorphism, glow, glossy effects, heavy shadows or decorative gradients.
- Archivo for display text, Inter for interface text, tabular figures for timers.
- Accessibility: never communicate status by colour alone, visible focus states, touch targets of about 44×44 px, respect `prefers-reduced-motion`.
- Polish UI strings are not repeated by hand across unrelated components; keep shared labels in one place.

## Domain rules

Read `docs/domain-model.md`, `docs/domain-glossary.md` and `docs/feedback-system.md` before changing domain behaviour.

- A workout plan has ordered blocks; a block has ordered items; an item is an exercise or a standalone break.
- Exercise modes: `rounds` and `continuous` (`strength` is reserved for later).
- The discipline is locked after the first exercise is added.
- Skipped or unrated exercises never enter averages and never count as a zero rating.
- Keep completion (how much was done) separate from execution quality (how well it was done).

## Scope

The current scope is in `docs/mvp-scope.md`. Out of scope unless the owner approves it explicitly: coach panel, social features, AI features, wearables, voice coaching, payments, full offline synchronisation, technique-by-technique combination builder.
